### Memory 주입 증거 — 시나리오 1의 2회차 요청 프롬프트 전문 (DEBUG)
`o.s.web.client.DefaultRestClient : Writing [ChatRequest...` 에서 추출. **2회차 요청의 `messages[]`가 1회차 USER+ASSISTANT로 시작**한다 = Memory가 프롬프트 조립 시점에 과거를 끼워 넣은 증거.

```
ChatRequest[model=qwen2.5, messages=[
  Message[role=USER,      content=2024-1234 어디쯤 있어요?],                 ← 1회차 USER (Memory 주입)
  Message[role=ASSISTANT, content=현재 라이더는 역삼역 사거리에서 배달 중입니다. ...下一步行动建议是什么？],  ← 1회차 ASSISTANT (Memory 주입)
  Message[role=SYSTEM,    content=[역할] ... [대화 맥락 사용 규칙] ... [응답 포맷] ...],   ← System Prompt
  Message[role=USER,      content=그거 언제 도착해요?]                        ← 2회차 새 USER
], tools=[getOrderDetail, getDeliveryStatus, cancelOrder ...]]
```

> 🔎 **관찰**: 메시지 순서가 `[과거 USER, 과거 ASSISTANT, SYSTEM, 새 USER]`. 즉 **Memory가 주입한 과거 메시지가 SystemMessage보다 앞**에 온다. SystemMessage가 대화 중간에 끼는 셈 — qwen2.5의 응답 언어 불안정(중국어 누수)과 연관 가능성. [관찰 2]

## 3단계 — JDBC / 재시작 실험

### Part 1. h2:file 영속성
2턴 대화(`jdbc-A`, "2024-1234 어디쯤?" → "그거 언제 도착?") 후 앱 종료 → **파일 직접 조회**:
```
$ java -cp h2.jar org.h2.tools.Shell -url 'jdbc:h2:file:./data/baedal;MODE=PostgreSQL' ...
CONVERSATION_ID | TYPE      | CONTENT55
jdbc-A          | USER      | 2024-1234 어디쯤 있어요?
jdbc-A          | ASSISTANT | 주문번호 2024-1234의 라이더는 현재 역삼역 사거리...
jdbc-A          | USER      | 그거 언제 도착해요?
(3 rows, 4 ms)
```
**재시작(같은 h2:file)** 후 `GET /session/jdbc-A/messages` → 대화 유지됨(1234 맥락 생존), `/session/ids` = `["jdbc-A"]`.
> ⚠️ 실행 중에는 4메시지였으나 `kill -9` 후 파일엔 3행 — 마지막 ASSISTANT 미플러시([관찰 8](../failure-observations/round3-failure-observations.md)).

### Part 2. h2:mem 휘발성
```
[mem1] 대화 1턴 후 /session/jdbc-mem/messages → [USER, ASSISTANT]  (있음)
[mem2] 재시작 후   /session/jdbc-mem/messages → []                  (소실)
       /session/ids → []
```

### 재시작 후 유지 표
| 저장소 | 재시작 후 유지? | 비고 |
|---|---|---|
| InMemory (기본) | ❌ | ConcurrentHashMap, JVM 종료 시 소멸 |
| `jdbc:h2:mem` | ❌ | 새 JVM = 새 mem DB |
| `jdbc:h2:file` | ✅ | 파일 영속 (kill -9 시 마지막 1건 유실 가능) |

### 부트 실패 → 우회 (관찰 4)
첫 시도 시 `No schema scripts found ... schema-h2.sql` 로 기동 실패. Spring AI 1.0.0은 H2 스키마 미동봉.
→ `spring.ai.chat.memory.repository.jdbc.platform=postgresql` 로 `schema-postgresql.sql` 강제 로드하여 해결.

### Part 3. 시나리오 5종 JDBC 재실행 (응답 거동 동일 확인)
jdbc 프로필(h2:mem)에서 1단계 5종을 그대로 재실행 → **InMemory와 동일하게 동작**:
| # | 결과 (JDBC) | 판정 |
|---|---|---|
| 1 | "그거" → 1234 도착시간 | ✅ |
| 2 | 취소 대상 1234→1235 전환 (cancelOrder 호출) | ✅ |
| 3 | "아까 물어본 그 주문" → 1234 | ✅ |
| 4 | s4b 맥락 없음 (세션 분리) | ✅ |
| 5 | DELETE 후 Memory `[]`, "그거" 해석 불가 | ✅ |

`/session/ids` = `["s1","s2","s3","s4a","s4b","s5"]`. 저장소(③)만 교체했을 뿐 ④·⑤ 로직이 동일하므로 응답 거동이 보존된다. (포맷 누수 `IMALACTION:`·`[예상 도착 시각]` 템플릿·중국어 등은 기존 qwen2.5 관찰의 재현 — [관찰 1·7](../failure-observations/round3-failure-observations.md).)
