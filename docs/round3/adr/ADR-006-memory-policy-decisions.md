# ADR-006 — 2단계 메모리 정책 결정 (윈도우 vs 요약 / 프로덕션 기준)

## Status
Accepted

## Context
2단계 실험(maxMessages 20/2/MAX)에서 윈도우의 한계가 드러났다. 윈도우 전략 자체의 대안·운영 기준·확장을 결정한다.

## 1) 슬라이딩 윈도우 vs 대화 요약(Summarization)
| 전략 | 장점 | 단점 | 적합 시나리오 |
|---|---|---|---|
| **슬라이딩 윈도우** (현재) | 단순·결정적, 라이브러리 제공(구현 0), 추가 LLM 호출 없음 | 윈도우 밖 정보 **완전 소실**(2단계 B 붕괴) | 짧은 거래성 상담(주문·배달 위치·단건 취소) |
| **대화 요약** | 긴 맥락을 압축 보존, 토큰 절약, 오래된 정보도 일부 유지 | 요약용 LLM **추가 호출**(비용·지연), 요약 과정의 손실·환각, "언제 요약할지" 판단 난해 | 길고 누적적 상담(분쟁·다건 환불·장기 케이스) |

→ Spring AI 1.0은 요약 메모리를 **기본 제공하지 않는다.** 필요하면 `ChatMemory`를 직접 구현(예: N턴마다/토큰 임계마다 요약). 배달 단건 상담은 윈도우로 충분, 분쟁 케이스는 윈도우+요약 하이브리드 검토.

## 2) 프로덕션 투입 금지 기준 (지시대명사 해결률)
- 2단계 실측: **A(20) 4/5 = 80%**, **B(2) 2/5 = 40%**.
- 배달 상담에서 "그거 취소"의 오해석 = **잘못된 주문 취소(비가역·금전 사고)**.
- **기준: 5턴 지시대명사 테스트에서 80% 미만이면 프로덕션 금지.** 근거: 취소·환불은 되돌릴 수 없어 5건 중 1건 오류도 분쟁으로 직결. → maxMessages=2(40%)는 즉시 탈락. 20(80%)은 **경계선** — 더 큰 모델 / 프롬프트의 [대화 맥락 사용 규칙] 보강 / 핵심 액션(취소) 전 재확인 가드 필요.

## 3) 배달 도메인에서 "오래된 대화"가 의미 있는 경우
- **3시간 전 주문**을 다시 문의(배달 지연 재확인) → 윈도우 밖이면 맥락 소실.
- **어제 환불 건** 재문의(처리 상태 추적).
- 한 세션에서 **여러 주문을 오가며 비교**("1234랑 1235 중 뭐가 먼저 와요?").

→ 단건·당일 상담은 윈도우로 충분하나, 위 경우는 **세션을 넘는 영속**(아래) 또는 요약이 필요. 윈도우 크기만 키우는 건 토큰 비용으로 한계.

## 4) Memory를 세션이 아닌 "고객 단위"로 영속하면
- **가능해지는 기능**: "지난주 그 환불 어떻게 됐어요?" 답변, 단골 주문 패턴 학습/선제 안내, 재문의 시 맥락 즉시 복원.
- **새 리스크**: ① 개인정보 **장기 보관**(법적 동의·보존기간) ② 저장 **폭증**(고객수 × 누적 이력) ③ **오래된 맥락 오적용**(작년 주소로 안내) ④ 프라이버시 사고 시 영향 범위 확대.

→ 현재의 **세션 단위**는 안전한 기본값. 고객 단위는 효용이 크지만 [ADR-005](ADR-005-memory-is-not-audit-log.md)(감사 분리) + 마스킹 + TTL + 동의 관리가 선행되어야 한다.
